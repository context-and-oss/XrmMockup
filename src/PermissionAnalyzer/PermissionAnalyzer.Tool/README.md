# XrmMockup Permission Analyzer

Find the Dataverse privileges your code needs and check whether your security roles grant them—without
running the code. Explore plugin steps, custom APIs, code activities, Azure Functions, and their calls
in a local browser UI or generate reports from the command line.

> **Preview.** This is static privilege analysis, not proof of record-level access. Ownership, business
> units, sharing, and runtime behavior can still affect access. Unresolved or incomplete analysis must
> not be treated as a pass.

## Install

You need .NET 10. The browser explorer also needs the ASP.NET Core 10 runtime, included with the SDK.
No Node.js installation is needed to use the packaged tool.

```bash
dotnet tool install --global XrmMockup.PermissionAnalyzer
```

For a repository-local installation:

```bash
dotnet new tool-manifest # only if the repository has no tool manifest
dotnet tool install XrmMockup.PermissionAnalyzer
```

Add `--prerelease` if installing a release candidate.

## Start here

You need a solution or C# project and, for role checks and metadata-driven suggestions, a local metadata
folder generated by `xrmmockup-metadata`.

**Explore in your browser:**

```bash
xrmmockup-permissions --solution Contoso.slnx --metadata ./Metadata --explore
```

**Generate a report:**

```bash
xrmmockup-permissions --solution Contoso.slnx --metadata ./Metadata --role "Salesperson" --detail normal
```

Run from the repository folder. You can omit `--solution` when the current directory contains a single
`.sln` or `.slnx`. If your paths are configured in `appsettings.json`, simply run `xrmmockup-permissions`.
Use `--no-roles` to inspect requirements without checking role coverage.

## Permission explorer

The explorer opens your default browser after the server starts. If no browser is available, open the
address printed by the CLI manually (default: `http://127.0.0.1:8765/`). Keep the CLI running while you
use the explorer; **Ctrl+C** stops it. If the port is occupied, add `--port 9000`.

1. **Choose what to analyze:** the whole model, a plugin, custom API, function, method, or table operation.
2. **Choose role coverage:** combine application/caller roles and, when needed, select impersonated
   caller roles separately. No explicit selection uses the session's CLI/configured defaults.
   **Requirements only** skips coverage; starting with `--no-roles` fixes that mode for the session.
3. **Run the query:** inspect requirements, granted/missing privileges, source traces, and warnings.
   Optional report filters narrow visible rows—not the analysis counts.

For table operations, **Changed columns** lets you search display or logical names and select columns.
You can remove selected chips or add a logical name manually. Changing the table clears the selection.
**No selection means unknown changed columns**, not “no changes”; filtered Update steps may be included.

The builder can be collapsed while you inspect results. Editing a query does not rerun it automatically;
a notice identifies results from the previous run. **Role catalog** searches individual role grants.
**Download JSON** exports the last completed query's report.

Toggle result badges (such as **Granted**, **Missing**, or **Unresolved**) to focus on one or more finding
types. **Filter columns** suggests values from the report as you search table, privilege, identity,
basis, and coverage; these filters combine with AND. Click a table heading to cycle ascending, descending, and original order. Display filters and
sorting apply across the result sections without rerunning the query or changing analysis totals or the
JSON export. **Clear result filters** restores all loaded rows. Completeness warnings remain visible;
matching sections retain their diagnostics. Results are grouped into one row per table, with permissions
listed inside it. Equivalent requirements share their source traces; different identities, assumptions,
bases, and coverage evidence remain distinct. A new query result resets these display controls.

The explorer is read-only and local. It does not run your code or change Dataverse. Inputs are loaded
once; restart the CLI to refresh them. Choose scopes, filters, and reports in the UI rather than combining
`--explore` with CLI query/report options such as `--operation`, `--format`, or `--strict`.

### Look up calling and impersonated users

Select **Connect to Dataverse** in the query builder, enter your environment URL, and choose browser,
device-code, or existing Azure CLI sign-in. Authentication runs in the local analyzer: complete browser
sign-in on that machine, or follow device-code instructions in its terminal. Nothing connects automatically.
After sign-in, the analyzer runs **WhoAmI** and shows the connected account’s name and sign-in address.
This account performs lookups; it does not automatically become the calling or impersonated user.

The form defaults to the root-level `DataverseUrl` and `DataverseCredentialType` settings from
`appsettings.json` (including environment-specific and environment-variable overrides). With `--explore`,
`--dataverse-url` / `-u` and `--credential-type` / `-t` override those defaults without requiring a user
argument or starting authentication. You can still edit both values in the form before connecting.

```bash
xrmmockup-permissions --snapshot permissions.snapshot.json --explore --dataverse-url https://your-org.crm.dynamics.com --credential-type azcli
```

- **Look up calling user** searches enabled/disabled users by the beginning of their name, email, or
  sign-in name. Select an enabled user to use their direct and team role assignments instead of explicit
  role selection.
- Expand **Impersonated caller roles** and select **Look up impersonated user** when app code acts for
  another user. Both identities are checked separately; team membership does not grant direct delegation.
  Users fixed by plugin/workflow registrations keep their captured identities; this selector does not
  replace registration metadata.
- The selected user's assignments show their lookup time and source teams. **Refresh assignments** reads
  them again. **Use role selection instead** returns that identity to offline role selection.
- **Disconnect** clears live selections. The saved analysis and previously displayed report remain unchanged.

User lookup reads live **assignments**, but privilege definitions still come from this session's local
metadata/snapshot. Missing or duplicate role definitions fail the lookup—refresh your metadata rather
than treating that as successful coverage. A selected user's assignments are held for this session and
are not refreshed automatically by each query. Neither credentials nor live selections are saved in a
snapshot. Query report exports can include user/assignment provenance; treat them as private.

This works with snapshot-only or snapshot-plus-metadata sessions that include role definitions. Fixed
requirements-only sessions cannot connect. The explorer remains loopback-only and never executes your
analyzed code or writes Dataverse records.

## Save once, explore offline

A snapshot saves the complete analysis so future sessions do not need the source project or another
compilation. Capture with metadata to include role definitions and column suggestions:

```bash
xrmmockup-permissions --solution Contoso.slnx --metadata ./Metadata --save-snapshot permissions.snapshot.json
xrmmockup-permissions --snapshot permissions.snapshot.json --explore
```

By itself, `--save-snapshot` saves the analysis and stops. Add `--explore` to open the browser after saving.
A snapshot is not a JSON report; files produced by `--format json` cannot be replayed.

To supply updated role grants and browser column suggestions:

```bash
xrmmockup-permissions --snapshot permissions.snapshot.json --metadata ./Metadata --explore
```

**What refreshes:** explicit `--metadata` replaces the role catalog. In the explorer, it also replaces
column suggestions for tables present in the supplied metadata; other tables retain saved suggestions.
If no column catalog is available, manual entry still works.

**What stays frozen:** captured code, lookup targets, plugin/workflow registrations, and request rules.
Supplying metadata does **not** reanalyze them. Create a new snapshot when those inputs change.

Snapshots also support CLI reports:

```bash
xrmmockup-permissions --snapshot permissions.snapshot.json --operation "Update account" --attributes name --role "Salesperson" --strict
```

Keep snapshots private: they can contain source paths, extracted literals, user IDs, and security-model
details. Secrets embedded in analyzed source are not scrubbed. Snapshot replay is offline unless you
explicitly connect for user lookup in the explorer or request it with `--user` or `--caller-user`.

## Common CLI queries

Examples use fictional role and entry-point names; replace them with names from your model.

| Task | Options to add |
|---|---|
| Inspect a plugin | `--plugin AccountPostPlugin` |
| Inspect a custom API | `--custom-api ctx_ProcessOrder` |
| Inspect an Azure Function | `--function ProcessOrder` |
| Inspect an explicit method | `--entry Contoso.Sync.Importer.Run` |
| Trace a table operation and its cascades | `--operation "Update account" --attributes name,ownerid` |
| Combine role grants | `--role "Salesperson" --role "Marketing"` |
| Check an impersonated caller separately | `--role "Integration App" --caller-role "Salesperson"` |
| List requirements without coverage | `--no-roles` |
| Find why code needs a privilege | `--table account --privilege Write --detail full` |

Choose at most one scope: `--plugin`, `--custom-api`, `--function`, `--entry`, or `--operation`.
Without a scope, the tool analyzes all entry points and unreached methods. Filters change displayed
rows only; they do not change totals, coverage, or exit codes.

For all options, run `xrmmockup-permissions --help` or see the
[command reference](https://github.com/delegateas/XrmMockup/blob/main/docs/permission-analyzer-reference.md#usage).

## Read the results

| Result | What it means |
|---|---|
| Granted | The selected roles grant the privilege at the reported depth. Record-level access is not verified. |
| Missing | The selected roles do not grant the required privilege. |
| Not checked | The relevant identity has no roles to check against. |
| Unverifiable | Available privilege metadata is insufficient to verify coverage. |
| Unresolved / incomplete | Some behavior could not be determined statically. Review the diagnostic; the requirements may be incomplete. |
| SYSTEM | No security role is required for that operation. |

`--detail normal` shows source locations and findings that need attention. Use `detailed` to include
granted requirements, SYSTEM operations, and assumptions; use `full` for every source and call path.
The default `minimal` report summarizes requirements or missing privileges. `compact` adds entry points.
Methods not reached from an entry point may need `--entry` if something outside the solution calls them.

Roles combine at the highest granted depth. The analyzer checks privilege presence, not whether that
depth covers a particular record. Application and impersonated caller identities are checked separately.

## Check permissions in CI

Use `--strict` to fail on missing privileges **and** incomplete checks:

```bash
xrmmockup-permissions --solution Contoso.slnx --metadata ./Metadata --role "Integration App" --strict
```

`--fail-on-missing` fails only on missing privileges; incomplete coverage can still exit successfully.
Without either flag, missing privileges do not fail the run.

| Exit code | Meaning |
|---|---|
| `0` | Run completed without a failure under the selected policy. |
| `1` | Missing privileges, or—with `--strict`—incomplete checks. |
| `2` | Invalid options, missing inputs, unknown roles, or another tool error. |

For file exports, add `--output` and choose `text`, `json`, `markdown`, or `sarif`:

```bash
xrmmockup-permissions --role "Integration App" --strict --format markdown --output permissions.md
```

Only analyze projects you trust: source loading invokes MSBuild and source generators. Do not analyze
untrusted pull requests with secrets or write credentials. In permission-gating checks, use reviewed
role metadata and configuration so a code change cannot grant itself privileges or suppress findings.

## Configuration and live roles

Settings belong under `XrmMockup:Permissions` in `appsettings.json`. A minimal example:

```json
{
  "XrmMockup": {
    "Permissions": {
      "Solution": "./Contoso.slnx",
      "MetadataDirectory": "./Metadata",
      "ExcludeProjects": ["*.Tests"]
    }
  }
}
```

Configured paths are relative to the configuration file. CLI options override configuration.
For application/user role mappings, accepted exceptions, request rules, and project exclusions, see the
[configuration reference](https://github.com/delegateas/XrmMockup/blob/main/docs/permission-analyzer-reference.md#configuration).

For CLI reports, only `--user` or `--caller-user` connects to Dataverse. The explorer also offers the
explicit connection and user lookup described above. These options read current direct/team assignments
and match them to your downloaded role definitions; keep metadata current. They cannot be combined with
`--role` or `--caller-role`, respectively. See
[live user role lookup](https://github.com/delegateas/XrmMockup/blob/main/docs/permission-analyzer-reference.md#checking-a-dataverse-users-actual-roles)
for authentication and examples.
